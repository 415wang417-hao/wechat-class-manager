### 预期（R̂）

本周计划产出：完整 C8 申请材料（proposal 5 部分 + AI 日志 + 拿来说明），以及一个**能在模拟数据上端到端跑通**的早期验证物原型：消息桥接 → 分类 → 挑战关联 → 提交矩阵 → QA 提取 → 周报，测试全绿，准确率过 70% 验收线。

### 实际（R）

本周实际产出：

1. `wechat-class-manager/` v0.2：9 个核心模块 + 3 份 JSON Schema + 4 份 SKILL.md + 23 个单元测试；
2. 端到端流水线一键运行，5 件产物（messages/linked/submissions/qa_pairs/weekly_report）；
3. 指标：分类准确率 **96.15%**、submission/question 召回 100%、提交事件 32 个、QA 对 12 个、挑战关联覆盖率 91.09%；
4. 完整申请材料 4 份（proposal / demo 说明 / AI 日志 / 拿来说明 / 本 AAR）。

### 差值（ΔR = R̂ − R）

- **完成了什么：** 全部预期项，且超出——周报引擎（reporter.py）原计划 W5–W6 才做，因流水线搭好后边际成本低，提前完成。
- **没完成什么：** 真实数据源（chatlog）未实测——原 R̂ 里也没排本周，不算缺口，但要防它变成"永远的下一步"。
- **意外发现：** ΔR 为负（超额）的部分集中在文档与封装：AI 协作让"写文档/封装/测试"的成本远低于预期，瓶颈反而在**人工审查每一份 AI 产物的耗时**。

### 失败分析

- **哪里失败了：** v0.1 有 3 个 bug：① 时间线压缩（10 天数据挤进 20 小时）；② 缺 AI 日志告警大面积误报（按单文件而非学生×挑战聚合）；③ 老师被计入活跃学生。另外 classifier.py 初版有定义顺序错误、测试夹具路径错一层目录。
- **根本原因：** AI 一轮生成大量代码时**用"代码能跑"代替了"语义正确"**——尤其 bug ②，是领域语义（学生会分两条消息提交）缺失导致的，单元测试没覆盖这个场景所以第一遍全绿也没发现。
- **不是根本原因但看起来像的：** "AI 能力不行"——不是。同样的 AI 在我给出明确的领域规则（分条提交、聚合判定）后一次修对了。根因是**我第一轮没把领域行为讲清楚**，把验证责任全推给了测试断言。

### 下周计划（若入选 → W1–W2）

- 基于本周 AAR，下周的 R̂ 调整为：**接通 chatlog 真实数据源并成功提取 Elite20 群 ≥100 条消息（脱敏后）**；同时把"学生×挑战聚合"这类领域行为写成显式的测试用例，不再依赖口头约定。
- 需要改变的做法：AI 产出后先做**产物级审查**（看输出内容对不对）再做代码级审查（看实现）——bug ② 就是产物审查抓到的，代码审查抓不到。
- 需要的支持：老师对班级群历史数据的脱敏使用授权。

### 拿来主义周更（强制项）

本周我发现了 **sjzar/chatlog 的 HTTP API 模式**，它比我原计划的自研 PyWxDump 解密方案更好，因为它把"数据库解密"这个高风险高工作量环节封装成了社区维护的成熟组件，我只需要写一个 30 行的适配函数——**风险转移给了维护者，我专注 Layer 2/3 的领域逻辑**。代价是端点格式受制于其版本迭代，已记入 W1 检索计划持续跟踪。
