## 二、逐来源取舍分析

### 来源 1：C8 方案（主要蓝图）

- **直接复用（adopted）：**
  - 三层架构 Layer 1/2/3 的模块划分——这是整个原型的骨架；
  - 标准消息 schema 的全部字段设计（msg_id/timestamp/sender/type/content/media_ref/reply_to）；
  - 七类意图标签及各自的信号特征定义（如 submission=文件+命名规范）；
  - 验收标准的量化写法（>70% 准确率、≥5 提交、≥10 QA）——直接变成我的测试断言。
- **去掉（removed）：**
  - Property Graph 存储（Neo4j/NetworkX）：当前规模 20 学生×8 挑战，SQLite+JSON 甚至纯 JSON 就够，先不上图数据库。**原因：申请阶段引入存储复杂度会拖垮"零依赖可运行"的验证优势**；Graph 存列为 W5–W6 的选型再评估项。
  - wechaty 双向写回：合规与复杂度不匹配，列入 Level 4 高阶选做。
- **重构（improved）：**
  - 分类实现：方案给的"规则 / LLM / 混合"三档 → 我实现成"规则引擎为主体 + `classify_with_llm()` 扩展点"的单一代码路径，规则先兜底、LLM 只处理低置信度样本，避免维护两套逻辑。
  - 提交检测：方案只说"文件 + 命名规范匹配"→ 我按学生×挑战聚合多条消息后判完整性（方案没考虑分条提交的真实行为，v0.1 的误报逼出了这个改进）。

### 来源 2：chatlog

- **复用：** 不自研数据库解密（PyWxDump 路线工作量大且来源风险高），桥接层按其 HTTP API 模式写适配函数 `fetch_from_chatlog()`。
- **取舍理由：** 对比 freestylefly/wechat-cli（Linux/macOS 限制）与 afumu/wetrace（取证级，杀鸡用牛刀），chatlog 是 Windows 可用 + 文档最全 + 社区最活跃的选项。
- **诚实边界：** 端点按当前文档写的是最小实现，未实测——接入周（W1–W2）第一件事就是跑通它。

### 来源 3：wechat-cli

- **复用：** CLI 参数设计（`--group/--days/--output`）与 JSON Lines 输出格式。
- **没拿：** 其提取内核（平台不支持我的环境）。

### 来源 4：SKILL.md 惯例

- **复用：** 四个模块各写一份 SKILL.md（触发词/用途/IO/依赖/调用示例/边界）。
- **改进：** 每个 SKILL.md 附"已验证指标"小节——把 C8 的验收数字写进技能说明，调用方能直接判断可信度。

### 来源 5/6：班级执行方案 + 自有 C5 资产

- **复用：** G1 提案结构 → proposal 骨架；AI_LOG 留痕要求 → AI 日志的轮次式写法；C5 的拿来说明格式 → 本文件。
- **改进：** C5 的拿来说明偏"清单式"，本次升级为"adopted/removed/improved 三栏 + 理由"，对齐 C8 评分标准的"取舍分析"要求。

## 三、组合出的新东西（创造性部分）

1. **三源切换桥接**（mock/file/chatlog）：方案只设想了单一数据源，仿真数据驱动 + 真实数据适配器的组合是我加的——它把"没数据授权"从阻塞项变成排期项；
2. **确定性仿真数据 + 剥离金标准的测试**：可复现（固定种子）、可复核（任何人重跑同结果）、防作弊（标签先剥离再分类）三合一；
3. **提交完整性聚合告警**：从 v0.1 误报中迭代出的领域逻辑，方案原文没有。
