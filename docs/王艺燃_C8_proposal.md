## 1. 项目选择

- **我选择的项目：** 微信群班级管理 Agent —— 把 Elite20 的班级微信群变成 Agent 可调用的管理系统：消息提取 → 意图分类 → 提交追踪 → Q&A 沉淀 → 自动周报。

- **为什么适合我：**

  - **我的相关经验：** C5 交付了开源项目 shipcheck（GitHub 仓库、README、AI 日志、拿来说明完整，体检 100/100 A 级达标）；C6A 做过提交数据仪表盘，熟悉"数据 → 结构化 → 可视化"的整条链路；本 proposal 附带的 `wechat-class-manager` 原型已经跑通了消息分类、提交矩阵、QA 提取和周报生成的端到端流水线。

  - **我在 C1–C7 中展示的相关能力：**
    - C1/C2：信息处理与结构化产出——本项目本质是把非结构化聊天流变成结构化数据；
    - C3：群内参与——我是群里回答问题较多的成员（原型模拟数据即以我的真实群内行为模式为蓝本），我切身体会过"好问题被聊天流淹没"的痛点；
    - C4/C5：可复用 Skill 封装与开源协作——本项目 4 个模块已按 SKILL.md 标准封装，可被任何 Agent 调用；
    - C6A：仪表盘——C8 的 Dashboard（Level 4）是 C6A 的自然升级。

  - **我对这个领域的理解：** 微信群已经是中国大学课程管理的事实标准，但它只是一条消息流。不需要替换它，只需要在上面加一层 Agent 智能层：数据桥接（让 Agent 看得见）→ 意图分类（让 Agent 看得懂）→ Skill 封装（让 Agent 能行动）。老师的核心痛点是提交追踪全靠手动翻群文件、问答沉淀全靠记忆——这两个都是可以被结构化数据直接消灭的。

### 拿来的部分（adopted）

- **三层架构**（Channel → Runtime → Skills）：我的模块划分直接对应 Layer 1/2/3；
- **标准消息 schema**（msg_id/timestamp/sender/type/content/media_ref/reply_to）：逐字段采用；
- **七类意图标签**（submission/question/answer/announcement/discussion/resource/social）：分类体系直接复用；
- **chatlog 作为数据源路线**：不做数据库解密轮子，桥接层留好适配器。

### 修改 / 删除 / 重构的部分

- **去掉** wechaty 双向写回（原因：申请阶段不需要写微信群，风险与复杂度不匹配，列入 Level 4 选做）；
- **重构** 消息分类为"纯规则引擎 + LLM 扩展点"混合架构（原因：方案给的 LLM 分类在无 API 预算时不可运行，规则引擎保证零依赖可验证，`classify_with_llm()` 保留升级路径）；
- **新增** 确定性模拟数据生成器 + 金标准测试集（原因：申请阶段无真实群数据授权，用可复现的仿真数据验证架构，这是方案里没有但端到端验证必需的一环）；
- **新增** 提交完整性聚合逻辑（原因：发现"先交正文后交 AI 日志"被单文件告警误报，按学生×挑战聚合才符合真实提交行为——v0.1→v0.2 的真实迭代，详见 AI 日志）。

## 3. 执行方案（KSTAR）

### K（Knowledge）：我已有的知识和资源

- **相关技能：** Python 标准库工程化（原型零依赖即可运行）、JSON Schema 设计、规则引擎设计、单元测试（unittest）；AI 协作工作流（C5/C6 已验证的多轮迭代方法）。
- **可用工具：** WorkBuddy（AI 编码协作，本原型即产物）、chatlog（待接入）、Git/GitHub。
- **团队 / 协作资源：** Elite20 班级群本身就是数据源与第一个真实用户（老师 = 客户）；可按方案建议组成双人协作（一人 Layer 1 数据源，我做 Layer 2/3）。

### S（Situation）：当前问题是什么

- **现状：** 原型 `wechat-class-manager` 已在模拟数据上端到端跑通：分类准确率 96.15%、提交召回 100%、32 个提交事件、12 个 QA 对、23/23 测试通过。但数据是仿真的，真实数据源的解密/适配尚未落地。
- **痛点：** ① 测试夹具与分类器同源，96% 存在偏差，需真实数据重新标定；② chatlog 端点对接未实测；③ 无增量处理（全量重跑）；④ 无人用（还没有真实用户）。
- **约束条件：** 真实微信数据涉及他人隐私，接入需老师授权 + 脱敏；API 预算单任务超 70 元需审批（方案红线）——所以规则优先、LLM 兜底的路线是对的。

### T（Task）：我要解决什么

- **核心目标：** 8 周内让系统在 Elite20 真实班级群上运行，老师能通过一句自然语言查询得到班级状态。
- **子任务分解：**
  1. **W1–W2：真实数据接入** —— 接通 chatlog，真实群 7 天消息提取成功（≥100 条），脱敏方案落地；
  2. **W3–W4：分类器真实标定** —— 人工标注 200 条真实消息为金标准，重测准确率（预期降至 70–85%），迭代规则字典至 >85%；
  3. **W5–W6：Skill 化 + 查询接口** —— 4 个 SKILL.md 可被 Agent 识别调用，自然语言查询支持 5 类问题（谁没交/谁最活跃/某挑战 FAQ 等）；
  4. **W7–W8：Watcher 闭环试运行** —— 增量处理 + 周报自动生成，在真实群运行 ≥1 周，老师验收。

### Â（Action Plan）：怎么做

| 子任务 | 执行步骤 | AI / 工具 | 输入 → 输出 |
|---|---|---|---|
| 数据接入 | 安装 chatlog → 解密 → 端点微调 → 脱敏映射表 | chatlog + AI 写适配代码 | 本地微信 DB → 真实 messages.jsonl |
| 标定 | 抽样 200 条 → 人工标注 → 重跑测试 → 修规则字典 | unittest + AI 分析误判样本 | 标注集 → 准确率报告 |
| Skill 化 | 补齐 IO schema 校验 → 在 Agent 运行时中实测调用 | Agent runtime | SKILL.md → 可调用验证记录 |
| 闭环 | checkpoint 增量机制 → 定时任务 → 周报发群 | cron/Agent hook | 消息流 → 周报 + 告警 |

### R̂（Expected Result）：预计产出什么

- **可交付物清单：**
  1. 真实数据版 `wechat-class-manager` GitHub 仓库（含完整 AI 日志与 AAR 序列）；
  2. 真实群数据上的分类准确率报告（目标 >85%，含 200 条标注集）；
  3. 4 个可被 Agent 调用的 SKILL.md + 5 类自然语言查询演示；
  4. 运行 ≥1 周的 Watcher 闭环 + 自动周报样例。
- **成功标准：** 老师在周会上说"这个周报有用，下周继续发"——真实用户认可，不是自嗨。
- **验证方法：** 每项产出可独立运行验证（测试命令写进 README）；周报被真实转发/引用即现实价值证据。
